# SQLite backup and recovery objectives

## Measurable targets

- RPO ≤ 24 hours: the first cohort may lose at most one daily backup window.
- RTO ≤ 2 hours: from incident confirmation to a serving restored instance.

## Drill

```bash
npm run backup:db
RESTORE_SOURCE=tmp/backups/mindiou-<timestamp>.sqlite npm run restore:db
```

The restore script checks source and target integrity, restores into a new directory, verifies WAL mode and table count, reports elapsed time against the RTO target, and removes temporary decrypted material. A restored test instance must then verify that sessions, reports and repayment state remain resumable.

## Acceptance checklist

- [ ] Backup is readable and `integrity_check` returns `ok`.
- [ ] Restore succeeds in a new directory without overwriting production.
- [ ] Sessions, reports and repayment state remain resumable after restore.
- [ ] SQLite WAL/SHM files are regenerated by the restored instance and journal mode remains WAL.
- [ ] Restore directory is 0750; database files are no more permissive than 0640 and owned by the service user.
- [ ] Backup storage is physically/logically separate from the production host.
- [ ] With `DATABASE_BACKUP_ENCRYPTION_KEY`, backups are `.sqlite.enc`; the key is not stored beside them.
- [ ] The same key can restore an encrypted backup and a wrong key fails closed.
- [ ] Drill records include backup time, restore start/end, RPO/RTO and failure reason.

The backup script keeps plaintext SQLite compatibility by default. Production should set `DATABASE_BACKUP_REQUIRE_ENCRYPTION=1` so a missing encryption key fails the backup instead of creating an unencrypted artifact.

## Alert acceptance

`npm run monitor:alerts` runs every five minutes and checks three consecutive health failures, AI failure rate above 10%, slow database writes, per-user cost anomalies, queue backlog, low disk space and a post-deploy error spike. It is read-only; systemd, the log collector or an on-call system can deliver notifications.
